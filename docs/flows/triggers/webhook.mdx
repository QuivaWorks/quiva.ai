# Webhook Trigger

A webhook trigger gives a flow a URL that an outside service can POST to. The request body becomes `$.trigger`, the flow runs, and the response goes back to the caller.

Underneath, it is a gateway mapping pointed at your flow — the same machinery as the [HTTP Request trigger](/flows/triggers/http-request). The difference is that the webhook trigger generates the path for you, opens it to the public, and hides the tuning controls.

| | Webhook | HTTP Request |
|---|---|---|
| Path | Generated: `/webhook/<collection>/<flow>` | You type it |
| Public by default | Yes, unless you issue a key | No |
| Editable settings | Public URL, API key | Public URL, API key, timeout, requests/second, invocation type, allowed hosts |

<Tip>
If you want to choose the path, keep the endpoint authenticated, or set a timeout, use the [HTTP Request trigger](/flows/triggers/http-request) instead. Everything on this page applies to it too.
</Tip>

---

## Creating one

Add a **Webhook** trigger from the **Add Node** panel. A **Create Webhook** dialogue opens showing the URL that will be created, a **Public** / **Secure** pill, a **Security** section for issuing an API key, and — if your account has more than one gateway — a gateway to pick. Press **Create**.

The pill reports the state rather than setting it: issue a key and it reads **Secure**. See [Security](#security).

The URL is fixed. It is built from your flow's own identifiers and there is nothing to type.

---

## The URL

```
https://<your-gateway-host>/webhook/<collection-id>/<flow-id>
```

`<your-gateway-host>` is your own gateway's hostname — a subdomain of the platform's API host, unique to that gateway. It is **not** `api.quiva.ai`, and there is no shared webhook host that every account posts to.

<Warning>
Do not construct the URL by hand. Open the webhook trigger node and copy the **Full URL** row — that is the only reliable source.
</Warning>

---

## Calling it

**POST only**, with a JSON body or none at all. The method is not configurable on the trigger.

```bash
curl -X POST "https://<your-gateway-host>/webhook/<collection-id>/<flow-id>" \
  -H "Content-Type: application/json" \
  -d '{"type":"payment.succeeded","data":{"object":{"id":"pi_3Q","amount":2500}}}'
```

Against a secured webhook, add the key:

```bash
curl -X POST "https://<your-gateway-host>/webhook/<collection-id>/<flow-id>" \
  -H "Content-Type: application/json" \
  -H "x-api-key: <your-api-key>" \
  -d '{"type":"payment.succeeded"}'
```

The header is `x-api-key`. There is no query-string form. Keys issued from a trigger panel are *restricted* keys — they carry an `msr-` prefix and are valid for that one endpoint and method only.

**A body that is present must be valid JSON**, and one that is not comes back as **400** with a JSON error body naming the parse failure. Form-encoded (`application/x-www-form-urlencoded`) and multipart bodies are refused on the same grounds, so a service that cannot send JSON cannot drive a webhook trigger.

An **empty** body is fine, though: a POST carrying nothing starts the run with `$.trigger` set to `null`.

Query parameters do reach the flow — not on `$.trigger`, but as headers. See [Query parameters](#query-parameters) below.

## Security

A webhook with no key is **public** — anyone who knows the URL can run your flow. Both the create dialogue and the trigger node let you fix that.

**At creation.** The **Create Webhook** dialogue has a **Security** section. Set **Expiry (days)** (365 by default) and press **Generate API Key**; the webhook is then created secured rather than public. The key is shown once, in that dialogue, and cannot be retrieved after it closes — copy it before pressing Create. If a key for this webhook's name already exists on the account, the dialogue surfaces that one instead and the webhook is created secured against it.

**Afterwards.** Open the webhook trigger node. It carries a **Public URL** toggle and a **Security** section that is always present, whichever state the webhook is in. Generating a key there also clears **Public URL**, since a key on a public endpoint protects nothing. Press **Save** — the toggle lives on the gateway mapping, not on the node, and Save writes both.

There is no regenerate. Rotating means deleting the key and generating a new one, which invalidates the old one at once.

<Tip>
An [HTTP Request trigger](/flows/triggers/http-request) starts authenticated rather than public. If the endpoint should be private, that is the safer default to begin from.
</Tip>

<Info>
A webhook does not check who is calling unless you add a **signature check**. Turn it on under [Verifying a signature](#verifying-a-signature) so only requests signed with your shared secret start the flow.
</Info>

<Warning>
There is no event filtering: every request that reaches the URL, and passes any signature check, starts the flow. Filter on `$.trigger` in a [Condition](/flows/steps/condition) step if you only want some of them. Nothing responds to a service's URL-verification challenge either.
</Warning>

## Verifying a signature

Many services sign each request with a secret you share. A signature check lets the trigger refuse any request that was not signed with that secret, **before** the flow starts.

Open the trigger node and expand **Verify signature**, then click **Add signature check**.

| Field | What it does |
|---|---|
| **Preset** | Fills the fields for a common sender: GitHub-style, Slack-style, plain body HMAC (hex) or Standard Webhooks. |
| **Scheme** | `HMAC SHA-256` signs the raw body (optionally with a template). `Standard Webhooks` follows the [Standard Webhooks](https://www.standardwebhooks.com) scheme. |
| **Secret** | A `SECRET::name::` reference to a secret you have stored. Only the reference is saved, never the value. |
| **Signature header** | The header that carries the signature. Required for HMAC SHA-256. Standard Webhooks defaults to `webhook-signature`. |
| **Encoding** | `Hex` (default) or `Base64`. HMAC SHA-256 only. |
| **Prefix** | Text before the signature, such as `sha256=`. HMAC SHA-256 only. |
| **Timestamp header** | A header with the send time in unix seconds. Standard Webhooks defaults to `webhook-timestamp`. |
| **Tolerance (seconds)** | How far the timestamp may differ from now, in either direction. 0 means 300 seconds. The maximum is 3600. |
| **Signed payload** (under **Advanced**) | What HMAC SHA-256 signs. The default is `{body}`. A template such as `v0:{timestamp}:{body}` signs the timestamp too. Use `{body}` exactly once. |

How it behaves:

- The check runs on the **raw request bytes** and compares in constant time. The flow then sees exactly the bytes that were verified. The body must be JSON.
- A request that fails the check gets **401** before anything runs. No run is recorded and nothing is queued. The logs name the check that failed, never the secret or the body.
- A request that passes is **not deduplicated**. Within the tolerance window, the same signed request starts the flow again, so build the flow to be safe to run twice.
- **Signed bodies are limited to 4 MiB.** A signed trigger refuses a larger body with 401. Flows without a signature check accept bodies up to the gateway's own limit.
- The check applies to calls that arrive through the gateway URL. It applies once the flow is published, and test runs are not verified.
- If you set a **Timestamp header** on HMAC SHA-256, the signed payload must include `{timestamp}`, and the reverse. Otherwise the timestamp would be checked but not signed, and an old request could be replayed with a fresh timestamp. The editor refuses that combination.
- Standard Webhooks takes no prefix or signed-payload template. Its secret is `whsec_` followed by base64, and it needs a `webhook-id` header. It accepts up to four `v1,` signatures, and any match passes.

<Tip>
To verify signed events inside the flow instead, for a scheme the check does not cover, use the `crypto` helpers in an [Eval step](/flows/steps/eval#crypto-helpers).
</Tip>

## Example: sync a tracker's events

A tracker usually posts several changes in one signed delivery. Use a signature check, split the delivery into items, and apply each item in its own run. This is the same sequence a [connected tracker](/essentials/account/connections) runs for you with no flow, so build it only when you want your own steps in the middle.

| Step | Configure |
|---|---|
| 1. Webhook trigger | Add a [signature check](#verifying-a-signature) with the tracker's scheme and your stored secret |
| 2. [Connector](/flows/steps/connector) | `sync_normalise` with `event` set to `$.trigger`. It returns `items` and writes nothing. |
| 3. [Condition](/flows/steps/condition) | Skip the next step when `items` is empty |
| 4. Quiva Endpoint | Subject `microstrate.hub.post.workflow-run` with `{"subject": "<child flow>", "triggers": "$.NORMALISE.items"}`. One child run starts per item. |
| 5. Child flow: [Connector](/flows/steps/connector) | `sync_apply` with `item` set to `$.trigger`. Creates or updates the task. |

Because the signature is checked before step 2, only deliveries signed with your secret get this far. The sync is safe to repeat: applying an item that is already in step writes nothing.

## Reading the request

`$.trigger` is the raw request body, unwrapped and with nothing added.

For this body:

```json
{
  "type": "payment.succeeded",
  "data": { "object": { "id": "pi_3Q", "amount": 2500, "currency": "gbp" } }
}
```

| Expression | Resolves to |
|---|---|
| `$.trigger.type` | `"payment.succeeded"` |
| `$.trigger.data.object.amount` | `2500` |
| `$.trigger.data.object` | the whole object |
| `Payment \|$.trigger.data.object.id\| for \|$.trigger.data.object.amount` | `"Payment pi_3Q for 2500"` |

Request headers are on `$.env.headers`, flattened to strings:

```
$.env.headers["Content-Type"]
$.env.headers["User-Agent"]
```

<Note>
Two different casings live in this map. A header **the caller sent** arrives in
canonical form — `Content-Type`, `User-Agent`, `X-Api-Key` — because Go's HTTP
server normalises it on the way in. A header **the platform added** for you is
lower-case: `x-method`, `x-url`, `x-account-id` and every `x-param-*`. Nothing
after the gateway re-cases either, so match what you see here exactly.
</Note>

<Warning>
There is no `$.trigger.headers`, no `$.trigger.webhook_id` and no `$.trigger.received_at`. Nothing about the request is added to the payload — if you need the delivery time, take it from a header the sender set, or generate one in a step.
</Warning>

### Query parameters

Anything in the query string arrives as a header named after it:

```
https://<your-gateway-host>/webhook/<collection-id>/<flow-id>?source=crm&tag=a&tag=b
```

| Expression | Resolves to |
|---|---|
| `$.env.headers['x-param-query-source']` | `"crm"` |
| `$.env.headers['x-param-query-tag']` | `"a,b"` |
| `$.env.headers['x-method']` | `"POST"` |

A repeated parameter is comma-joined into one value. A parameter that was not sent is absent, and reading it resolves to `[]`.

<Tip>
A sender you do not control — a service that appends its own tracking parameters, say — is best read this way and copied onto a value of your own in a [Map step](/flows/steps/map) before anything branches on it.
</Tip>

## The response

The caller waits for the flow and gets back JSON:

```json
{
  "tracking_id": "…",
  "status": "…",
  "result": { }
}
```

`result` is every step's output by default. Set the flow's **Final Response Mapping** (in the flow's settings) to a JSONPath object and `result` becomes exactly that instead — the usual way to hand a sender the shape it expects.

<Note>
There is no `executionId`, no `executionTime` and no `error.code` envelope. A run that errors still returns this shape; the failure shows in `status` and in **Monitoring**.
</Note>

## Draft and published flows

**A webhook always runs the published flow.** The mapping is created against the published subject even when you build it on a draft, so:

- Before the flow's first publish, calls arrive with nothing to run.
- Editing and pressing **Save** changes nothing about what the webhook executes. Press **Publish**.

This differs from most other triggers, which bind to whichever version was open when you created them.

<Note>
**What runs after the trigger is decided by each step's outcome, not by the arrows in the editor.** A Condition step's outcome names the step IDs to run next — one, several (they start at the same time), or the reserved `RESOLVE_SUCCESS` / `RESOLVE_ERROR` to end the run. A line drawn between two steps that no outcome names is decoration.
</Note>

## Troubleshooting

<AccordionGroup>
  <Accordion title="The sender reports 400 invalid_request_body">
    The body is not valid JSON. `details.reason` in the response carries the parser's own message. A sender that posts form-encoded data hits this every time.
  </Accordion>

  <Accordion title="401 or 403">
    The webhook is secured and the caller is not sending `x-api-key`, or the key has expired. Keys default to a 365-day expiry. A **401** with no run recorded can also mean the [signature check](#verifying-a-signature) failed: check the secret, the header name, the encoding and the clock, and that the body is under 4 MiB.
  </Accordion>

  <Accordion title="The URL 404s">
    Check the flow has been published at least once. Then re-copy the **Full URL** from the trigger node rather than trusting a URL written down earlier.
  </Accordion>

  <Accordion title="The flow ran but a step read nothing">
    `$.trigger` is the request body with nothing wrapped around it, so a path that assumed a wrapper resolves to `[]`. Open the run in **Monitoring** and read the recorded trigger.
  </Accordion>

  <Accordion title="Only some events should start the flow">
    All of them do. Put a Condition step first and branch on a field of `$.trigger`.
  </Accordion>

  <Accordion title="A browser call is blocked by CORS">
    Add the site's origin under **Allowed Hosts** on an HTTP Request trigger. That list is a property of your account's gateway, shared by every endpoint on it — it is not per-trigger.
  </Accordion>
</AccordionGroup>
