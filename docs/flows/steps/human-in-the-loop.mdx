# Checkpoint Step

A Checkpoint step stops the run and hands it to a person. It creates a task, notifies the people you named, and parks the run until somebody continues it — by answering a form on the task, or from the Monitoring page. Whatever that person sends back becomes the step's result.

The step is called **Checkpoint** when you add it to a flow; its node type is `human-in-the-loop`.

---

## Configuration

The editor has a **General** tab (name, ID and description), a **Notifications** tab with five fields, and a **Form** tab for answering on the task.

<ParamField path="title" type="string">
The title of the task created for the assignees.
</ParamField>

<ParamField path="description" type="string">
A summary of the situation that needs a decision. Becomes the task's description.
</ParamField>

<ParamField path="assignees" type="string">
A **comma-separated list of user IDs**. The editor is a user picker, so you choose people rather than typing IDs. Leave it empty and the step falls back to the account's configured escalation responders.
</ParamField>

<ParamField path="priority" type="string">
One of `lowest`, `low`, `medium`, `high`, `highest`. Sets the task's priority.
</ParamField>

<ParamField path="message" type="string">
**Escalation Message** — the body of the notification sent to each assignee.
</ParamField>

Like every step payload, these are JSONPath-resolved before the step runs, so a message can quote the run:

```json
{
  "title": "Approve refund for |$.trigger.order_id",
  "description": "$.CLASSIFY.result",
  "assignees": "$.static.approvers",
  "priority": "high",
  "message": "Order |$.trigger.order_id| needs a decision before it can proceed."
}
```

### Form tab

Add form fields to let the assignee answer on the task itself instead of from Monitoring.

<ParamField path="fields" type="object">
**Form fields** — the questions, built with the schema builder. Leave it empty for the Continue-only behaviour described below.
</ParamField>

<ParamField path="task_id" type="string">
**Use an existing task** — a task ID, or a path to one such as `$.CREATE_TASK.id`. Leave it empty to create a new task.
</ParamField>

<ParamField path="keep_status" type="boolean">
**Don't change the task status** — answering the form leaves the task in its current status.
</ParamField>

## What happens when the run reaches it

<Steps>
  <Step title="A task is created">
    A task is opened in the **ESCALATE** space with your title, description and priority, assigned to the people you named. It carries the run ID and the flow's subject in its metadata.
  </Step>
  <Step title="Assignees are notified">
    Each assignee is emailed. The email links to the task and to the run itself, at `/en/hub/monitoring?run-id=…&highlight-continue=true` — which opens Monitoring with the **Continue** control highlighted.
  </Step>
  <Step title="The run parks">
    The run's status becomes **paused**, and its remaining graph and collected data are stored so it can be picked up later. Nothing downstream runs. There is no expiry: a paused run waits indefinitely.
  </Step>
  <Step title="Somebody continues it">
    If the step has form fields, the task carries an action that opens the form. Submitting it resumes the run with the answers, and a comment on the task names who answered. Otherwise, or in addition, a paused run shows a green **Continue** button on the Monitoring page. It opens a dialog with one field — a message to pass as the output of the paused step — and resuming restarts the run from that step.

    To resume through the API (`POST /hub/workflows/run`), pass the run's full tracking ID as `run_id`, in the form `ms.hub.run.<uuid>.<flow subject>`, and the response as `trigger`. A bare run uuid is rejected with `400`, and a run that isn't paused or errored returns `409`.
  </Step>
</Steps>

## What the step returns

**The values from the task form, or exactly what the person typed into the Continue dialog.** With form fields, the result is the object the form produces. Through Continue, the step imposes no shape on it: there is no `approved` flag, no `reviewer`, no `comments` and no timestamp. If a later step needs to branch on a decision, the resumer has to supply it and you have to read it back yourself.

<Warning>
The Continue dialog's message field must be **JSON**. Type `{"approved": true, "note": "fine"}` and the step's result is that object; type bare prose and Continue refuses it. Agree a small JSON shape with whoever is going to action these, say so in the escalation message, or give the step form fields so the shape is fixed for you.
</Warning>

<Note>
Resuming a run that is not paused, for example one already answered, is refused with a `409`. A second submit of the same form is refused too.
</Note>

```json
{ "approved": true, "note": "Refund authorised, under the £200 threshold" }
```

```
$.my_checkpoint.approved
$.my_checkpoint.note
```

The same message is also available on its own, at `$.resume`, to any step after the Checkpoint. `$.trigger` is untouched by the resume and still holds the payload that started the run.

<Note>
`$.resume` exists only on a run that was resumed, and it is set whether the run was continued from a pause or retried after an error. On a run that has never been resumed, reading it gives `[]`.
</Note>

A Condition step after the Checkpoint can then route on it:

```json
[
  { "condition": { "operator": "=", "input": ["$.my_checkpoint.approved", true] }, "outcome": "ISSUE_REFUND" },
  { "outcome": "CLOSE_AS_DECLINED" }
]
```

## What it does not do

<Warning>
- **No quorum.** Any single Continue resumes the run, however many people were assigned. There is no "2 of 3" or "all approvers".
- **No timeout.** A paused run has no expiry and no automatic approve, reject or escalate. It waits until a person acts or somebody cancels it.
- **No approval buttons.** There is no set of named options to choose from — approval is whatever the form or JSON contains, interpreted by your own Condition step. A dropdown field in the form is the closest thing.
- **No structured display.** The person sees the task's title, description and priority. There is no separate data panel showing values from the run; put anything they need to see into the description.
</Warning>

---

## Finding paused runs

Monitoring counts paused runs separately and can filter to them. A paused run's detail panel offers **Continue** (resume from the paused step) and **Rerun** (start again from the beginning with a new trigger). Both are also available on a run that has errored.

<Note>
Editing a flow changes its **draft**. **Publish** to make a change take effect. A run already paused resumes on the configuration it was paused with, not on whatever has been published since.
</Note>
